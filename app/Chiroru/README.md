# Chiroru

В **0.7.0** добавлен точный профиль заводской прошивки `1982735225` (Android 11,
32-битный userspace, ядро `5.4.125-ab1982735225`). APK собирается для
`arm64-v8a` и `armeabi-v7a`; на этой станции устанавливается 32-битная версия.
Backend не использует захардкоженное KASLR-смещение: база линейного маппинга
вычисляется из `memstart_addr` и `vabits_actual` загруженного ядра. Профиль
поддерживает in-app root, процессную консоль и ADB root; KernelSU для этой
сборки не собирался. ADB-модуль пересобран под заводской vermagic, клиент —
статический 32-битный. Обе цепочки проверены с холодной загрузки.
Подробности: [FIRMWARE.md](FIRMWARE.md).

В **0.6.5** исправлен пропуск служб KernelSU: в модуль перенесён обработчик
`EVENT_SERVICES` UAPI 5, необходимый встроенному `ksud` 3.4.2. Повторный вызов
служб в одном lifecycle пропускается, а `post-fs-data` открывает новый lifecycle.
Если KernelSU уже загружен, Chiroru не повторяет скрипты модулей поверх него.
Для применения обновлённого модуля требуется перезагрузка станции.
Дочерний процесс получает контекст `ksu` через явный `GRANT_ROOT`, поскольку
модуль восстанавливает Enforcing ещё внутри `insmod`. Уведомление переходит в
состояние выполнения до bootstrap; после смены UID обновления уведомления
пропускаются, а boot-отчёт сохраняется и при ошибке.
Автозагрузка запоминает kernel boot ID: перезапуск Android framework с новым
`BOOT_COUNT` больше не запускает bootstrap повторно в том же ядре.

В **0.6.4** автозагрузка доступна только в настройках. Задержка задаётся в
секундах от включения станции: 0–86400, по умолчанию 180. Изменение сохраняется
и пересчитывает уже ожидающий запуск; само по себе не включает автозагрузку.

В **0.6.3** обновлено оформление Material 3 Expressive: контрастная типографика,
лаймовый и лавандовый акценты, формы `MaterialShapes`, кнопки с анимацией формы
при нажатии и компактная панель навигации. На главной выделены статус и одно
основное действие, сведения о текущих правах показаны отдельно. Выбор метода
остаётся в настройках: плитки анимируют цвет и скругление, на широком экране
располагаются в два столбца. Под ними — описание выбранного способа. Обновлены
светлая/тёмная темы, журнал и консоль.

В **0.6.2** способ получения root выбирается в **«Настройках»**: Probe,
In-app root shell, ADB root shell или KernelSU. Под выбором показано, что именно
делает этот способ; выбор сохраняется между запусками. На главной остаётся одна
кнопка **«Получить root»**, которая запускает только выбранный способ. Если способ
не поддерживается текущим профилем, кнопка недоступна и другой способ не
запускается вместо него.

Получение root разрешено только на **Яндекс Станции Дуо Макс** (`chiron`,
`YNDX-00055`) с точным совпадением проверенного профиля прошивки. Проверка есть
и в интерфейсе, и в native-слое; на других устройствах и неизвестных сборках
ни один способ не запускается.

В **0.6.1** консоль работает и после **«Получить только root»**, сразу, без
перезапуска приложения и без модулей ядра. Root включён автоматически; команды
начинаются в `/` и выполняются в enforcing-домене `chiroru_console`.

Этот доступ живёт до завершения процесса Chiroru. При обычном сворачивании он
сохраняется; после force-stop/перезапуска приложения нужно снова получить root.
Команды выполняет отдельный пользовательский процесс, связанный с Chiroru
приватным наследуемым каналом. В режиме «Включить root для ADB» сохраняется
прежний модульный путь, работающий до перезагрузки станции.

Подготовка процессной консоли использует краткое permissive-окно существующего
bootstrap, затем возвращает Enforcing **до** допуска команд. В память загружается
политика с отдельным enforcing-доменом; файлы системных разделов не меняются.
Подробнее: [root-console](../../root-console/README.md).

В **0.6.0** добавлена вкладка **«Консоль»** для ввода команд на самой колонке:

- Нажмите поле «Команда», введите команду экранной клавиатурой и нажмите
  «Выполнить» или Enter. Вывод stdout/stderr появляется по мере выполнения.
- В обычном процессе используются права приложения. Переключатель **Root** доступен,
  если загружен обновлённый модуль и live-проверка подтверждает enrollment Chiroru.
  Для ADB root shell выберите способ в настройках и нажмите «Получить root» на главной.
- Если приложение только что включало модуль ADB/KernelSU, вкладка предложит **«Перезапустить
  Chiroru»**. Эта кнопка запускает чистый процесс приложения и возвращает в
  консоль; модуль остаётся загруженным. Это необходимо из-за изменений credentials
  при bootstrap. Для In-app root shell в 0.6.1+ перезапуск не требуется.
- «Стоп» завершает группу процессов команды, включая обычные конвейеры;
  закрытие процесса приложения также закрывает канал управления исполнителем.
- Вывод ограничен последними 65 536 символами, его можно выделить/скопировать
  и очистить. Черновик сохраняется при переходах между вкладками; вывод и
  команды не записываются в постоянный журнал.
- Каждая команда запускается в новом shell, исходный каталог — filesDir Chiroru.
  Например: `cd /data/local/tmp && ls -la`. `cd` не переносится на следующий запуск.
  Это командная консоль без PTY и ввода stdin: `top`/`vi` и интерактивный `read`
  не поддерживаются. Намеренно отделившиеся daemon-процессы не входят в группу
  команды и не относятся к гарантии остановки обычных дочерних процессов.

Root-консоль не запускает KernelSU Manager. Доступ выдаётся только отдельному
исполнителю с enrolled UID/SID; после описанного перезапуска UI-процесс без root.
Native runner тестируется задачей `:app:testConsoleRunner`, модель выполнения
и UI — `:app:testDebugUnitTest`.

В **0.5.0** добавлена отдельная кнопка **«Включить root для ADB»**. Она загружает
небольшой модуль `chiroru_adb`, устанавливает клиент и позволяет открыть с компьютера:

```sh
adb shell -t /data/local/tmp/chiroru-su
```

KernelSU для этого режима не нужен. Консоль работает с UID 0 в enforcing-домене
`chiroru_adb`, после закрытия приложения и до перезагрузки станции. Сам Chiroru
после перезапуска распознаёт модуль через read-only API без выдачи ему root.
Режим «Получить только root» по-прежнему относится к процессу приложения.
Детали реализации, bootstrap и сборки: [ADB root](../../adb-root/README.md).

В 0.4.2 при открытии и возвращении в приложение проверяется текущее состояние:
UID/EUID главного потока Chiroru и наличие загруженного KernelSU. Поддержка
прошивки показана отдельно от фактических прав. Старые отчёты не восстанавливают
root нового процесса. При подтверждённом KernelSU повторная root/module операция
блокируется; обнаружение само по себе не запускает установку Manager или lifecycle.

На `5000001307` у обычного Chiroru SELinux закрывает `/proc/modules`, а seccomp
может блокировать запрос KernelSU. В этом случае отображается «текущее состояние
недоступно», а не отсутствие root. Проверка не выдаёт приложению доступ в Manager.
Подробности: [FIRMWARE.md](FIRMWARE.md#проверка-текущего-состояния-в-042).

Самостоятельная версия Android-приложения на **Kotlin + Jetpack Compose + Material 3 Expressive**.
Имя в лаунчере и уведомлениях — **Chiroru**, application ID — `dev.chiron.chiroru`.
Gradle-проект находится в отдельной папке; для native-сборки нужны соседние
каталоги из полного checkout. См. [инструкцию репозитория](../../README.md).

## Что перенесено

- Главная: диагностика Mali, получение root, загрузка KernelSU, результат последней операции.
- Журнал: отчёты текущего сеанса и загрузки устройства, выделение текста, копирование и отправка.
- Настройки: системная/светлая/тёмная тема с палитрой Chiroru, автозагрузка.
- Kotlin-сервис и receiver для direct boot: настраиваемая задержка от включения станции (по умолчанию 180 секунд).
- Проверка KSU Next Manager после загрузки KernelSU и установка официального APK, если менеджера нет.
- Нативная библиотека и оба бинарных ресурса исходного приложения.
- Русские и английские строки, адаптивная иконка, Compose Preview.

## Сборка

Нужны JDK 17–21, Android SDK platform 36, NDK `28.2.13676358`, CMake `3.22.1`.
Gradle Wrapper включён в проект. Зависимости скачиваются из Google Maven и Maven Central.

```bash
./build-apk.sh
# Результат: Chiroru.apk — оптимизированная release-сборка

./build-apk.sh --debug
# Для отладки: Chiroru-debug.apk
```

Скрипт выбирает установленный JDK 17, если `JAVA_HOME` не задан. SDK берётся из
`ANDROID_HOME`, `ANDROID_SDK_ROOT` или `$HOME/Android/Sdk`. Локальный `local.properties`
содержит путь SDK текущей машины и исключён из контроля версий.

Для Android Studio откройте эту папку как Gradle-проект и выберите Gradle JDK 17 или 21.

```bash
JAVA_HOME=/usr/lib/jvm/java-17-openjdk ./gradlew :app:testDebugUnitTest :app:lintDebug
adb install -r Chiroru.apk
adb shell am start -n dev.chiron.chiroru/.MainActivity
```

Обычное открытие приложения показывает интерфейс без вызова JNI. Сохранены существующие
CLI-режимы `--es mode probe`, `--es mode root`, `--es mode root+ko`,
`--es mode root+adb` (отдельный модуль ADB, без KernelSU).

Release-сборка использует R8, удаление неиспользуемых ресурсов и ART-профили библиотек;
отладка в ней отключена. APK подписывается тем же локальным debug-ключом, что и первая
версия, поэтому его можно установить обновлением без удаления данных. Это локальная
подпись для станции, а не отдельный ключ публикации.

На станции с Android 11 переходы между вкладками не накладывают два экрана друг на друга,
размер карточки состояния меняется без покадрового перерасчёта. Положение прокрутки вкладок
сохраняется. Палитра обоев удалена; внешний вид не зависит от Android 12+.

## Поведение загрузчика

Начиная с 0.3.5 основной APK включает проверенный на chiron 5000001307 модуль
KernelSU с транзакционным обновлением SELinux policy и точным подсчётом её размера.
В 0.4.0 добавлены профили прошивок: общий загрузчик выбирает native-реализацию,
модуль и CLI по точному совпадению признаков устройства и сборки. Профиль показан
на главной странице. Сейчас в каталоге два точных профиля:
`chiron-5000001307` (root и KernelSU/ADB root) и заводская `chiron-1982735225`
(root-only). Для неизвестной прошивки доступны сведения о сборке, а root и
загрузка модуля не запускаются. Это относится и к CLI-режимам, и к автозагрузке после OTA.
Перед загрузкой ресурсы заново извлекаются из APK в отдельный каталог профиля
с проверкой SHA-256. Порядок добавления прошивки: [FIRMWARE.md](FIRMWARE.md).

В 0.4.1 поддержка обычного root и KernelSU разделена. Профиль может содержать
только `root.backend`, без `.ko` и `ksud`; поддержка KernelSU описывается отдельным
необязательным блоком. Один проверенный root-backend можно использовать для
нескольких точных сборок, независимо от готовности их модулей KernelSU.
Главная страница показывает доступность обоих режимов. Автозагрузка относится
только к KernelSU и не подменяется обычным root при отсутствии его поддержки.

Заводская сборка `1982735225` — Android 11 с 32-битным userspace (`armv8l`);
APK содержит native-библиотеки и `armeabi-v7a`. Для неё реализован только
root-профиль: база линейного маппинга вычисляется по `memstart_addr` и
`vabits_actual`, без захардкоженного KASLR-смещения. Модуль KernelSU и ADB root
для этой сборки ещё не пересобраны, поэтому каталог не объявляет их поддержку.


Автозагрузка по умолчанию **выключена** и включается в настройках. У Chiroru отдельный
идентификатор, поэтому старое приложение можно оставить установленным; автозагрузку
следует включать только в одном из них. Настройка и ресурсы хранятся в device-protected
storage и доступны до разблокировки. Номер загрузки предотвращает повторный запуск
из-за двух boot broadcasts.

Нативные операции выполняются на главном потоке, как в исходном приложении: текущий
нативный код зависит от thread group leader. UI показывает состояние ожидания перед
вызовом, но анимации и взаимодействие приостанавливаются на время выполнения JNI.
Это ограничение текущего переноса. Отчёт появляется целиком после завершения вызова.

После сообщения об изменении состояния ядра повторные root-операции в том же процессе
блокируются; диагностика и журнал остаются доступны. Перезапуск процесса требуется
перед повторной попыткой, но сам по себе не подтверждает совместимость с устройством.

## Автоматическая установка KSU Next Manager

После подтверждённого результата «KernelSU загружен» Chiroru проверяет пакет
`com.rifsxd.ksunext`. Это работает при ручной загрузке и при автозагрузке. Уже установленный
менеджер остаётся на месте: Chiroru не обновляет, не заменяет и не удаляет его.
Режимы диагностики и «только root» эту процедуру не запускают.

Режим `root+ko-safe` также проверяет и устанавливает менеджер, но пропускает скрипты
запуска модулей. Если в обычном режиме эти скрипты завершаются ошибкой, интерфейс
показывает «KernelSU загружен с ошибками»: загруженный модуль и полученный root сохраняются,
а установка менеджера остаётся доступной. Ошибка записывается и в отчёт автозагрузки.

Ожидание `ksud` ограничено 60 секундами, скриптов запуска — 120 секундами по монотонным
часам. Закрытый stdout, заполненный буфер журнала и непрерывный вывод не отменяют таймаут.
При превышении срока останавливается группа дочернего процесса; основной поток не ждёт
его завершения без ограничения, чтобы продолжить восстановление SELinux Enforcing.

Если менеджера нет, Chiroru получает последний стабильный релиз через официальный
[GitHub API KernelSU-Next](https://api.github.com/repos/KernelSU-Next/KernelSU-Next/releases/latest),
выбирает обычный `KernelSU_Next_…-release.apk` (вариант `spoofed` исключён) и скачивает его
по HTTPS. Проверяются размер, SHA-256 из метаданных GitHub, имя Android-пакета, минимальная
версия Android и сертификат подписанта. Ожидаемый SHA-256 сертификата совпадает с
`EXPECTED_MANAGER_HASH` исходного модуля:

```text
79e590113c4c4c0c222978e413a5faa801666957b1212a328e46c00c69821bf7
```

Установка запускается через системный `pm install` от уже полученного root, с передачей APK
через stdin. Флаг замены существующего пакета не используется. Результат проверяется повторным
запросом PackageManager, а временные данные APK очищаются. Для этой станции используется пользователь 0.
Команда — `pm install --user 0 -S <размер>` без завершающего `-`: прошивка Android 11
считает отдельный `-` неизвестной опцией, а при отсутствии пути читает stdin автоматически.
Именно эта команда успешно установила официальный KSU Next v3.4.2 на станции;
`pm path com.rifsxd.ksunext` подтвердил наличие установленного пакета.

Сеть, проверка APK и передача данных выполняются вне UI-потока. До JNI открываются файловые
дескрипторы для скачивания и boot-отчёта; они сохраняют доступ на запись после изменения
credentials нативным кодом. Проверка APK и передача в `pm` используют путь `/proc/self/fd/N`
к дублированному дескриптору, поэтому приватный путь через каталог приложения с правами
`0700` повторно не открывается. Права на сам каталог приложения не меняются. Вызовы смены
UID из приложения не используются: Android 11 блокирует их через seccomp. Получение root и
запуск дочернего `pm` остаются на главном потоке. Сам нативный алгоритм не меняется.

Состояние показывается на главной странице, подробности — в журнале. Если GitHub недоступен,
подпись изменилась или установка завершилась ошибкой, KernelSU остаётся загруженным;
кнопка «Повторить установку менеджера» повторяет только проверку/скачивание/установку.
Автозагрузка сохраняет результат в `boot-report.txt`. Для первого скачивания нужен Интернет.

## Совместимость и версии

Это перенос существующего загрузчика для целевого устройства, а не расширение списка
поддерживаемых ядер. Смещения ядра остаются специфичными для этой станции. JNI-обёртка
поддерживает Kotlin-класс и выбор запуска хуков; нативный код включает исправления очистки
окон памяти, запуск хуков и общий обработчик ожидания дочерних процессов.

- Целевое устройство — станция с Android 11 (`minSdk 30`), ABI `arm64-v8a`.
- `targetSdk 30` сохранён для поведения сервиса и direct boot на исходном Android 11.
  Повышение target SDK требует отдельного переноса правил foreground services и boot.
- Kotlin `2.2.20`, AGP `8.13.2`, Gradle `8.14.3`.
- Compose `1.10.5`, Material 3 `1.5.0-alpha10` с настоящими `MaterialExpressiveTheme`,
  `MotionScheme.expressive()` и `LoadingIndicator`.
  Эта версия закреплена для имеющегося SDK 36 / AGP 8; Expressive API экспериментальные.

Официальные источники: [Material 3 в Compose](https://developer.android.com/develop/ui/compose/designsystems/material3),
[версии Material 3](https://developer.android.com/jetpack/androidx/releases/compose-material3).

## Проверки

`testDebugUnitTest` проверяет распознавание результатов JNI, блокировку повторных операций
после частичного изменения ядра, навигацию, выбор релиза, установку отсутствующего менеджера,
ошибки сети/подписи/установки и отсутствие повторной установки существующего пакета. UI-тесты используют
Robolectric на Android 11 и подставные обработчики: native-код при них не вызывается.
Проверки профилей покрывают точный выбор сборки, отказ для неизвестных и неоднозначных
профилей, выбор отдельной native-реализации, хеши ресурсов, обновление кеша и режимы запуска.
Также проверяются root-only без бинарных ресурсов, независимость root от backend
KernelSU, общая root-реализация для разных сборок и доступность кнопок/автозагрузки.
Задача `verifyFirmwareCatalog` входит в `preBuild` и проверяет соответствие каталога,
скомпилированных backend ID и бинарных ресурсов до сборки APK.
`testFirmwareCatalog` входит в `check` и проверяет валидатор на root-only и полных профилях.
Сборка и JVM-тесты не заменяют проверку загрузки на физическом целевом устройстве.

`ManagerDeviceTest` отдельно проверяет обычный доступ IO-потока к файлам, обнаружение уже
установленного менеджера и реальное скачивание/проверку официального APK на Android.
При проверке APK тест временно запрещает обход собственного тестового каталога и убеждается,
что обычный путь выдаёт EACCES, а проверка подписи и передача всех байтов через дескриптор работают.
Эти проверки не запрашивают root и не устанавливают менеджер.

Установка отсутствующего менеджера проверена через подставной backend.
Проверка обнаружения установленного менеджера пропускается, если пакет на станции отсутствует.

`testNativeProcessWait` компилирует на компьютере только обработчик дочерних процессов
и проверяет таймауты, EOF, переполнение буфера, непрерывный вывод, сигналы и остановку
группы процессов. Нужны Python 3 и компилятор C (`cc` либо переменная `CC`). Задача входит
в `check`; root и код работы с ядром в этих тестах не запускаются.

```bash
JAVA_HOME=/usr/lib/jvm/java-17-openjdk ./gradlew :app:testNativeProcessWait :app:testDebugUnitTest :app:lintDebug
```

Для проверок устройства используйте отдельный application ID `dev.chiron.chiroru.preflight`:
тестовый runner сможет удалить тестовый пакет, сохранив установленный Chiroru и его процесс.

```bash
JAVA_HOME=/usr/lib/jvm/java-17-openjdk ./gradlew :app:connectedDebugAndroidTest -Pchiroru.preflight=true -Pandroid.testInstrumentationRunnerArguments.class=dev.chiron.chiroru.ManagerDeviceTest
```

Для обычной сборки `-Pchiroru.preflight=true` не передаётся; `./build-apk.sh` собирает
основной пакет `dev.chiron.chiroru`.

Состав и происхождение нативных файлов описаны в [SOURCES.md](SOURCES.md).
