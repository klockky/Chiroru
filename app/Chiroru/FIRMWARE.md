# Профили прошивок Duo Max

## Совместимость

Все профили относятся к Android 11, устройству `chiron`, модели `YNDX-00055`
и страницам памяти 4096 байт. Ядро — ARM64; factory использует 32-битный userspace.

| Сборка | ABI приложения | In-app root | ADB root | KernelSU |
|---|---|---|---|---|
| `5000001307` | `arm64-v8a` | Проверен | Проверен | Проверен |
| `5000001245` | `arm64-v8a` | Проверен | Проверен | Проверен |
| `1982735225` | `armeabi-v7a` | Проверен | Проверен | Проверен |
| `5000001248` | `arm64-v8a` | Проверен | Проверен | Проверен |

Zygisk/LSPosed на factory и `1245` не проверены. На `1307` LSPosed после поздней
загрузки Zygisk требует перезапуска Android framework; Chiroru его не выполняет.

## Каталог и выбор профиля

Каталог: [`app/src/main/assets/firmware/profiles.json`](app/src/main/assets/firmware/profiles.json),
схема 3. Профиль выбирается только при единственном точном совпадении всех полей
`match`: `device`, `model`, `fingerprint`, `incremental`, `sdk`, `kernelRelease`,
`machine`, `pageSize`. Подбора по ближайшему номеру прошивки нет.

| Поле | Назначение |
|---|---|
| `id` | Идентификатор профиля и имя каталога извлечённых ресурсов |
| `label` | Название в интерфейсе |
| `match` | Признаки устройства, прошивки и ядра |
| `root.backend` | Реализация root и диагностики |
| `adbRoot` | Необязательный блок: `backend`, `module`, `loader`, `client` |
| `kernelSu` | Необязательный блок: `backend`, `module`, `ksud`, `manager` |

Каждый ресурс содержит путь внутри APK и SHA-256. `kernelSu.manager` задаёт
источник (`OFFICIAL_RELEASE` или `BUNDLED`), пакет, versionCode и SHA-256
сертификата. Для встроенного менеджера обязателен ресурс `apk` с хешем файла.

`PROBE` и `ROOT` используют только `root.backend`. `ADB_ROOT` требует полный
блок `adbRoot`, а `MODULE` и `MODULE_SAFE` — полный `kernelSu`. Частично
заполненный блок считается ошибкой. Поддержка одного режима не подразумевает
поддержку остальных.

У factory менеджер устанавливается из APK до запуска KSU. У arm64-профилей
используется официальный менеджер v3.4.2; отсутствующий пакет устанавливается
после загрузки KSU. Несовместимый пакет блокирует KSU до нативного вызова,
но не влияет на Probe, In-app root и ADB root.

## Путь выполнения

```text
UI / intent / BootReceiver
  → Loader
  → FirmwareEnvironment → FirmwareCatalog
  → FirmwareRunner → FirmwareAssets
  → NativeBridge → backend_registry → backend
```

Общие классы находятся в `app/src/main/java/dev/chiron/chiroru/firmware/`,
нативный реестр — в `app/src/main/cpp/backend_registry.def`.
Ручной запуск и автозагрузка используют один `Loader`.

Ресурсы извлекаются из APK в device-protected `files/firmware/<profile-id>/`
при каждом запуске режима, с проверкой хешей и заменой через временный файл.
Несовпадение профиля или хеша даёт `preflight: blocked` до вызова root.
Сервис автозагрузки сохраняет такой отказ без повторных попыток.

Root и загрузка модуля выполняются одним нативным вызовом на главном потоке.
После изменения credentials повторная операция в этом процессе запрещена.
Таймаут `ksud` — 60 секунд, скриптов модулей — 120 секунд. При таймауте
завершается группа дочернего процесса, затем загрузчик восстанавливает Enforcing.

`ksud` читает `/proc/kallsyms`, поэтому на время загрузки KSU `kptr_restrict`
снимается. После `insmod` прежнее значение возвращается из домена `ksu`:
KernelSU восстанавливает Enforcing внутри загрузки модуля, и app-домен уже
не может писать этот sysctl.

## Адреса и ABI

Общий движок — `app/src/main/cpp/backends/chiron_5000001307/root.c`.
Он выбирает адреса ядра и способ вычисления линейной базы по точному профилю.

| Сборка | Kernel release | `sys_call_table - _stext` |
|---|---|---|
| `5000001307` | `5.4.125-android11-2-g601513d4b115-ab5000001307` | `0xEEE6E8` |
| `5000001245` | `5.4.125-android11-2-g601513d4b115-ab5000001245` | `0xEEE700` |
| `5000001248` | `5.4.125-android11-2-g601513d4b115-ab5000001248` | `0xEEE718` |
| `1982735225` | `5.4.125-android11-2-g85fe5498964f-ab1982735225` | `0xEEE548` |

Factory и `1248` вычисляют линейную базу из загруженного ядра:

```text
PAGE_OFFSET = -(1 << vabits_actual)
lbase = PAGE_OFFSET - memstart_addr
```

Для factory физические адреса: `memstart_addr=0x20620c8`,
`vabits_actual=0x2097b20`, `kimage_voffset=0x20620d8`, `init_task=0x22f7480`.
Для `1248` адреса и проверка Image header описаны в [анализе OTA](../../tools/ota/5000001248.md).
Каждое отображение физической памяти использует новый PTE-слот: очистка записи
не сбрасывает кеш TLB.

Все `.ko` собраны под AArch64, с точным vermagic и `module_layout=0x8395960f`.
Исходный vendor-коммит полного дерева сборки неизвестен; совместимость
подготовленных заголовков проверяется отдельно. Factory также требует
AArch32-хуков, armv7-демона и менеджера UAPI 5.
См. [сборку модулей](../../tools/KERNEL_MODULES.md) и [factory KernelSU](../../tools/factory/README.md).

## Проверка текущего состояния

`RuntimeStatus` хранит фактические права процесса и состояние модулей:

- `processRoot` — UID/EUID главного потока равны нулю;
- `kernelSu` — `LOADED`, `NOT_FOUND` или `UNKNOWN`;
- ADB root и процессная консоль проверяются через их действующие API.

Для KernelSU сначала читается `/proc/modules`, затем выполняется read-only
`GET_INFO` в дочернем процессе с таймаутом 500 мс. Если SELinux закрывает список
модулей, а seccomp блокирует запрос, результат — `UNKNOWN`. Это возможно и при
работающем KernelSU. Наличие менеджера и сохранённый отчёт не подтверждают
текущую загрузку модуля.

Проверка выполняется при открытии приложения, возврате в него и перед
автозагрузкой. Подтверждённый root или загруженный модуль блокирует повторный
bootstrap. Проверка сама не выдаёт права в Manager и не запускает службы.

## Добавление прошивки

1. Получите точные признаки сборки: `Build.*`, `uname` и размер страницы.
2. Извлеките ядро из OTA и проверьте драйвер, адреса, структуры и ABI модулей.
   [Инструменты анализа OTA](../../tools/ota/README.md) находят `sys_call_table`;
   остальные адреса требуют отдельной проверки.
3. Добавьте профиль в `profiles.json` и реализацию в нативный реестр.
   Для нового исходного файла обновите `CMakeLists.txt`.
4. Подготовьте ресурсы поддерживаемых режимов, запишите их хеши и параметры
   совместимого менеджера. Проверьте отказ для соседних и смешанных identity.
5. Соберите приложение из этого каталога:

   ```sh
   ./build-apk.sh :app:testDebugUnitTest :app:lintRelease \
     :app:testFirmwareCatalog :app:testNativeFirmwareProfiles :app:testNativeProcessWait
   ```

6. На целевой прошивке проверьте каждый режим после отдельной перезагрузки:
   root, SELinux-контекст, Enforcing, менеджер и службы KSU. Запишите результат
   в таблицу совместимости. Сборка APK и host-тесты не проверяют работу на устройстве.
