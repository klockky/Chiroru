# Профили прошивок Duo Max

## Единый APK в 0.7.3-rc2

Добавлен точный **тестовый** профиль `5000001248`, подготовленный по OTA.
В UI он помечен `OTA test`. KernelSU проверен на устройстве в rc2;
отдельные In-app/ADB root и автозагрузка ещё ожидают проверки;
статические основания, адреса и хеши: [5000001248](../../tools/ota/5000001248.md).

Схема каталога **3** добавляет обязательный `kernelSu.manager`: источник
(`OFFICIAL_RELEASE` или `BUNDLED`), пакет, versionCode и SHA-256 сертификата.
Для встроенного менеджера также обязателен `apk` с SHA-256 всего файла.
Выбор делает только exact-профиль; UI, intent и boot service используют общий
`FirmwareRunner`. Несовместимый менеджер блокирует MODULE и MODULE_SAFE
до native-вызова, но не ROOT/ADB_ROOT/PROBE.

Для factory пользователь устанавливает встроенный armv7-менеджер через
системный установщик из Chiroru, затем запускает KSU. Официальный менеджер
v3.4.2 выбирается профилями `5000001307`, `5000001245` и кандидатом `5000001248`; автоматического
перехода на будущий `latest` нет. Существующий пакет с другой подписью не
заменяется. Boot service не открывает установщик: отсутствие нужного менеджера
записывается как preflight-ошибка в boot-отчёт.

Release-проверка проверяет обе ABI в готовом APK, ресурсы всех профилей и
совпадение factory-демона в менеджере и загрузчике. Factory проходит аппаратную
проверку; повторная аппаратная проверка `5000001307` требует устройства с этой
прошивкой. Его проверенные kernel payloads сохранены.

Проверка 0.7.1: 108 JVM/UI-тестов, release lint, host-проверки native identity
и relocation штатных ADB-модулей. На factory после отдельных
перезагрузок проверены In-app root, ADB root и KSU с установленным мета-модулем:
Enforcing, `kptr_restrict=2`, lifecycle завершён. Android preflight проверил
сертификат встроенного менеджера и доступный системному установщику content URI.
Тестовый APK использовал отдельный package ID и был удалён после проверки.

Проверка 0.7.2 на `5000001245`: 109 JVM/UI-тестов, release lint, host-проверки
native identity и relocation для трёх ADB-модулей. На чистом устройстве после
отдельных перезагрузок проверены In-app root (uid 0, Enforcing), ADB root
(`u:r:chiroru_adb:s0`, `kptr_restrict=2`) и KSU (lifecycle complete,
`u:r:ksu:s0`, маркеры `post-fs-data`/`services`/`boot-completed`, менеджер
показывает «Работает», LKM, UAPI 5, v3.4.2). `kernelsu.ko`, `chiroru_adb.ko`
и ADB-клиент установлены из профиля `1245`.

## Выбор метода и ограничение устройства в 0.6.2

Метод получения root хранится в настройках как стабильный ID (`probe`, `in_app`,
`adb` или `kernelsu`); сохранение выбора не меняет состояние ядра. На главной
показываются выбранный метод и одна кнопка запуска. Probe остаётся только
диагностикой Mali и не получает root.

Каталог по-прежнему требует exact matching. Дополнительно проверяется, что
устройство — `chiron` / `YNDX-00055`: это сравнение есть в UI-модели, в
`FirmwareCatalog`/`FirmwareRunner`, в `Loader` и в native JNI bridge. Поэтому
чужое устройство, неизвестная сборка или подменённый `FirmwareSelection` не
запускают ни root primitive, ни извлечение payload. Автозагрузка использует
только KernelSU и не следует сохранённому методу.

## 5000001245

Третий точный профиль — `chiron-5000001245` (Android 11, `RQ3A.210805.001.A1`,
ядро `5.4.125-android11-2-g601513d4b115-ab5000001245`, 64-битный userspace).
Ядро собрано из того же коммита `601513d4b115`, что `5000001307`, поэтому
профиль использует те же проверенные константы layout.

Совместимость проверена по образу, прочитанному с загруженного устройства:
полные 21721088 байт `Image` (PA `0x1080000`) совпали по структуре с `1307`,
все 43482 общих текстовых символа имеют одинаковое смещение от `_stext`
(`module_layout` — `0x1a65ac`), а `init_task` (PA `0x22f7500`) и
`selinux_state` (PA `0x24fd000`, `enforcing` по смещению `0x311`) прочитаны
непосредственно. Один data-символ отличается: `sys_call_table` находится по
`_stext + 0xEEE700`, а не `0xEEE6E8`, как у `1307`. При старом значении KSU
патчил соседние syscall-слоты (`rt_sigreturn` вместо `reboot`), поэтому
GRANT_ROOT не работал. Для `1245` закреплён собственный массив смещений;
слоты 48, 79, 142, 147, 221 и 281 указывают на `faccessat`, `newfstatat`,
`reboot`, `setresuid`, `execve` и `execveat`.

`kernelsu.ko` и `chiroru_adb.ko` пересобраны под vermagic
`…ab5000001245`; `module_layout` совпадает с `0x8395960f`, как у штатного
`mali.ko` из OTA и у модулей `5000001307`. Отличие от `1307` также в identity
и в том, что при первом запуске lifecycle выполняет `ksud install`, создавая
`/data/adb/ksu` на чистом устройстве.

Официальный менеджер v3.4.2, `ksud` и ADB-клиент — общие arm64-ресурсы.

## 5000001248 — OTA candidate

В `0.7.3-rc1` добавлен четвёртый exact-профиль с отдельными модулями.
`sys_call_table` найден по `_stext + 0xEEE718`. База linear mapping берётся
из runtime `memstart_addr`/`vabits_actual`, а не из калибровки другой прошивки.
Перед обращением к globals проверяется ARM64 header по ожидаемому physical
Image base. Сборка модулей и статические проверки доступны без установки OTA;
В rc2 устранено повторное использование PTE-слота после проверки заголовка;
root stage, KSU module и lifecycle проверены на работающей `1248`, с итоговым
Enforcing и внешним `su` в контексте `u:r:ksu:s0`. Отдельные In-app/ADB root
и автозагрузка ещё не проверены.

## Заводская 1982735225

Добавлен второй точный профиль — `chiron-1982735225` (заводская Android 11,
`RQ3A.210805.001.A1`, ядро `5.4.125-android11-2-g85fe5498964f-ab1982735225`).
Его userspace только 32-битный (`armv8l`), ядро — arm64; APK теперь собирается
для `arm64-v8a` и `armeabi-v7a`, и на этой сборке устанавливается 32-битная
версия native-слоя.

Профиль объявляет `root`, отдельный `adbRoot` и собственный `kernelSu`.
Каталог не подставляет модуль от `5000001307`: для ADB root используется
пересобранный `chiroru_adb.ko` с заводским vermagic
`…g85fe5498964f-ab1982735225` и статический 32-битный `chiroru-su`.

Модуль собран не из исходника заводского коммита (его нет на станции), а из
подготовленных заголовков 5.4.125, которыми собраны проверенные модули
`5000001307`. Совпадение проверено по `module_layout = 0x8395960f` (такое же
значение у заводского `factory-mali.ko`), по `BUILD_BUG_ON` для `cred`,
`task_struct`, `file` и по точному vermagic. Release-guard модуля заменён на
заводскую строку. Это кросс-сборка с exact-проверкой ABI, а не сборка из
исходника прошивки; профиль ограничен точной identity и закреплёнными SHA-256.
KernelSU использует отдельный модуль, AArch32-хуки и совместимые armv7-демон и
менеджер на UAPI 5. Подробности и исходные патчи: [factory](../../tools/factory/README.md).

Для этой сборки backend не использует калиброванную «магию» `init_task.tasks.next`.
База линейного маппинга вычисляется из значений `memstart_addr` и `vabits_actual`
самого ядра:

```
lbase = PAGE_OFFSET - memstart_addr
PAGE_OFFSET = -(1 << vabits_actual)
```

Адреса переменных найдены в проверенном заводском образе и привязаны к точному
профилю: `memstart_addr` — PA `0x20620c8`, `vabits_actual` — PA `0x2097b20`,
`kimage_voffset` — PA `0x20620d8`, `init_task` — PA `0x22f7480`. Это устраняет
зависимость от конкретного KASLR-размещения при загрузке.

На устройстве с холодной загрузки проверены: reclaim страницы Mali, вычисление
базы при новом KASLR-смещении, обход списка задач, запись credentials, disarm
seccomp, загрузка policy и процессная консоль в `u:r:chiroru_console:s0`, а также
ADB root через `chiroru_adb.ko` и `/data/local/tmp/chiroru-su`
(`u:r:chiroru_adb:s0`, Enforcing). Модуль не персистентен: после перезагрузки
ADB root нужно включить снова. Никаких операций с разделами, загрузчиком или
обновлением профиль не выполняет.

## Консоль режима ROOT в 0.6.1

Схема каталога и exact matching сохранены. Операция ROOT не извлекает и не
загружает `.ko`/ksud: её userspace-исполнитель поставляется как native executable
в подписанном APK. Только после успешного выбора известного root backend Loader
готовит приватный канал. Backend включает подготовку исполнителя в существующее
bootstrap-окно и возвращает успех консоли после восстановления Enforcing и live
проверки. Отсутствие `root_console: ready` означает ERROR, даже если UID успел
стать нулевым; повтор после изменённых credentials по-прежнему запрещён.

ConsoleScreen допускает работу в изменённом процессе только при наличии живой
процессной консоли. Для ADB/KernelSU bootstrap сохраняется прежнее предложение
перезапустить приложение. Наличие процессной консоли не выводится из saved reports.
Детали: [root-console](../../root-console/README.md).

## Enrollment встроенной консоли в 0.6.0

Формат каталога и backend ADB сохранены. Обновлён только хеш `.ko`; старый
`chiroru-su` совместим. Перед root primitive backend считывает UID и полный
`/proc/self/attr/current` и передаёт их в параметры модуля `console_uid` и
`console_context`. При невозможности получить ожидаемую идентичность операция
останавливается до bootstrap. Статус консоли проверяется отдельным ioctl на
каждом обновлении runtime, без использования сохранённого отчёта.

CONSOLE_GRANT — отдельный от shell-only ADB_GRANT запрос. Он сверяет UID/EUID,
SID с MCS, initial user namespace, opener и current credentials, требует
однопоточность. Устанавливать эти параметры может только привилегированный
загрузчик при загрузке модуля. Политика SELinux и права device node не расширены.
Root получает дочерний native runner, исполняемый из защищённого nativeLibraryDir,
а не многопоточный ART-процесс. Переключатель Root недоступен со старым модулем.

## Независимый ADB root в 0.5.0

Схема 2 расширена необязательным `adbRoot`: `backend`, `module`, `loader`, `client`.
Все три ресурса проверяются по SHA-256 до native. Операция `ADB_ROOT` использует
`chiron-5000001307-adb`; KernelSU-ресурсы и lifecycle для неё не выбираются.
`loader` переиспользует CLI `ksud` исключительно для `insmod` с relocation;
поддержка самого KernelSU в профиле не требуется. Нет fallback на `MODULE`/`ROOT`
при отсутствии блока. Автозагрузка остаётся только KernelSU.

Native-реализация использует тот же root primitive с отдельным путём загрузки:
два vendor data symbols вместо четырёх, пустые параметры модуля, установка
`chiroru_adb.ko.client` в `/data/local/tmp/chiroru-su`, настройка типа устройства,
проверка read-only ioctl и scoped восстановление `kptr_restrict`. Успех `ADB_ROOT`
требует отдельного маркера `adb_root: ready` после восстановления Enforcing и не
трактуется как успех KernelSU/установки Manager.

Runtime GET_INFO модуля доступен обычному приложению; GRANT ограничен UID 2000
в домене shell. Найденный ADB root блокирует повторный root/bootstrap в UI/Loader.
Проверены clean-boot запуск без KernelSU, интерактивная консоль, force-stop/reopen
и отказ приложению. См. [отчёт](../../reports/chiroru-adb-root-device-2026-11-01.md).

## Проверка текущего состояния в 0.4.2

`RuntimeStatus` отделён от результата операции и возможностей прошивки:

- `processRoot`: фактические UID/EUID главного потока равны нулю;
- `kernelSu`: `LOADED`, `NOT_FOUND` или `UNKNOWN` по свежим сведениям;
- успешный прошлый отчёт не считается доказательством текущих прав;
- обнаружение модуля не подтверждает выполнение lifecycle и не запускает Manager.

`RuntimeDetector` читает `/proc/modules` с точным совпадением имени `kernelsu`
и состояния `Live`. При отсутствии положительного результата выполняется
read-only `GET_INFO` из UAPI KernelSU. Native-запрос изолирован в дочернем процессе
с исходными правами и seccomp; таймаут — 500 мс. Дочерний процесс получает fd
через штатные magic-значения KernelSU в syscall `reboot`, которые не являются
допустимыми magic-значениями Linux для перезагрузки. SIGSYS завершает только
дочерний процесс. Дескриптор закрывается; SU/lifecycle ioctl не вызываются.

Если список модулей недоступен и API не ответил, результат — `UNKNOWN`.
Наличие APK Manager, `/sys/module/kernelsu` и сохранённые флаги не используются
как доказательство загрузки. На проверяемой сборке `/sys/module/kernelsu` вообще
отсутствует при загруженном модуле. Права в Manager автоматически не выдаются.

Проверка выполняется при старте Activity, ON_RESUME и перед загрузкой из сервиса;
чтение и запрос выполняются на IO-потоке, UID/EUID берутся на главном потоке.
Intent ждёт завершения начальной проверки. Подтверждённые root/KernelSU блокируют
повторный root-вызов в UI и общем Loader, не подделывая результат операции.
При недоступных сведениях ручной запуск остаётся возможен; это не подтверждение
того, что KernelSU отсутствует.

Проверка 2026-11-01: 66 JVM/UI-тестов, lint Release, тесты каталога и native
process-wait прошли (`/tmp/opencode/chiroru-0.4.2-checks.log`). APK 0.4.2/code 21
обновил единственный установленный Chiroru. SHA-256 APK:
`07ceacd2efed8cf95a1599b3709fdeaffd4e25250dc309a633cd8f76058b3944`.
Хеши упакованных `.ko` и `ksud` совпадают с каталогом.

Два force-stop/cold-start и возврат в существующий процесс подтвердили:
`modulesReadable=false driverQuery=-1` (SIGSYS/seccomp),
`processRoot=false KernelSU=UNKNOWN`. UI показывает «Состояние проверено»,
«KernelSU: текущее состояние недоступно» и «Процесс Chiroru: без прав root».
Пользователь выбрал проверку без выдачи Chiroru доступа в Manager; автоматическое
распознавание загруженного модуля для этого UID на текущей прошивке недоступно.
Положительный путь детектора проверен JVM/UI-тестами, но не подтверждён этим
обычным UID на устройстве. Отдельный read-only ADB/su-запрос подтвердил, что модуль
по-прежнему `Live`, при неизменившемся kernel boot ID.
SELinux — Enforcing, обновлятор отключён, файл настроек Chiroru отсутствует
(автозагрузка по умолчанию выключена). Root/module операции не повторялись.

## Структура с версии 0.4.0

```text
UI / intent / BootReceiver
          ↓
Loader                         состояние процесса, главный поток, отчёт
          ↓
firmware/FirmwareEnvironment    Build + uname + размер страницы
          ↓
firmware/FirmwareCatalog        точное совпадение с profiles.json
          ↓
firmware/FirmwareRunner         операция + выбранный профиль
          ├── FirmwareAssets    извлечение и SHA-256 ресурсов
          └── FirmwareBackend   интерфейс нативного исполнения
                    ↓
NativeBridge → backend_registry → backends/<реализация>/
```

`firmware/` расположен в `app/src/main/java/dev/chiron/chiroru/`.
JNI и нативный реестр — в `app/src/main/cpp/`.
UI не содержит адресов ядра и не выбирает модуль самостоятельно.
Ручной запуск, `--es mode …` и сервис автозагрузки используют один `Loader`.

## Контракт профиля

Единственный каталог — `app/src/main/assets/firmware/profiles.json`, схема 3
(начиная с 0.7.1; прежние схемы заменены вместе с ресурсом APK).
В каждой записи:

- `id`: стабильное имя профиля; используется также как каталог кеша;
- `label`: название для интерфейса;
- `match`: точные `device`, `model`, `fingerprint`, `incremental`, `sdk`,
  `kernelRelease`, `machine`, `pageSize`;
- `root.backend`: ID проверенной реализации обычного root и диагностики из
  `app/src/main/cpp/backend_registry.def`;
- необязательный `kernelSu`: отдельно проверенная поддержка KernelSU;
  `kernelSu.backend` выбирает реализацию полного запуска root+модуль,
  `kernelSu.module` и `kernelSu.ksud` задают пути внутри APK и SHA-256 файлов;
  `kernelSu.manager` закрепляет источник, пакет, сертификат, versionCode и
  ресурс встроенного APK, когда источник — `BUNDLED`.

Для root-only профиля блок `kernelSu` отсутствует или равен `null`:

```json
"root": { "backend": "chiron-5000001307" },
"kernelSu": null
```

Это фрагмент записи, а не готовый профиль другой прошивки: `match` по-прежнему
содержит все проверенные признаки конкретной сборки. Несколько записей могут
ссылаться на один `root.backend` и иметь разную поддержку KernelSU.
Для текущей `5000001307` оба режима поддерживаются и указывают на существующий
backend `chiron-5000001307`; хеши бинарных ресурсов сохранены.

`PROBE` и `ROOT` проверяют только `root.backend` и не открывают ресурсы KernelSU.
`MODULE` и `MODULE_SAFE` требуют полный блок `kernelSu`, его backend и оба
ресурса. Частично заполненный блок считается ошибкой каталога, а не root-only.
Отсутствие или ошибка ресурсов KernelSU во время исполнения не мешает отдельному
root-вызову: этот путь их вообще не читает.

В интерфейсе независимо показывается доступность root и KernelSU. У root-only
профиля доступна кнопка «Получить только root», но загрузка KernelSU и включение
её автозагрузки недоступны. Сохранённую настройку автозагрузки можно выключить.
Если она осталась включённой после смены прошивки, сервис получает отказ от
общего runner, сохраняет отчёт и завершает попытку. Автозагрузка не переключается
на обычный root автоматически.

При отсутствии совпадения или нескольких совпадениях профиль не выбирается.
Версии не сравниваются по диапазону, номеру «ближайшей» сборки или одному `5.4.125`.
Совпадение идентификаторов выбирает проверенную конфигурацию; само по себе оно
не доказывает совместимость приватного ABI ядра.

Неизвестная сборка получает диагностический отчёт с фактическими признаками
устройства. Mali-диагностика вызывается только через подходящий backend.
Отказ профиля или проверки ресурсов помечается `preflight: blocked`; сервис
автозагрузки записывает отчёт и не повторяет такую попытку три раза.

## Нативная реализация

`backend_registry.h` определяет интерфейс: диагностический отчёт и операция
root с необязательными путями модуля/CLI и флагом запуска lifecycle hooks.
JNI передаёт только ID и параметры операции. Реестр не имеет реализации
«по умолчанию» для неизвестного ID.
Root-only вызов передаёт `null` вместо путей ресурсов и выключает lifecycle.
Полный root+KernelSU остаётся одним native-вызовом, чтобы сохранить порядок
смены credentials, загрузки модуля и восстановления SELinux. Раздельные ID
в каталоге позволяют выбирать разные реализации, не разрывая эту последовательность.

Текущая реализация — `backends/chiron_5000001307/root.c` (бывший `mali36449.c`).
Один движок обслуживает несколько точных профилей: смещения `task_struct`,
физические адреса `init_task`/`memstart_addr`/`vabits_actual`, поправки
vendor-символов и способ вычисления линейной базы выбираются по профилю.
Никакого выбора «по ближайшей версии» нет. Диагностика Mali JM вынесена в
`backends/mali_jm_probe.c`; процессные таймауты и вспомогательные функции общие.
Флаг lifecycle передаётся на каждый вызов, а не хранится глобально.

Если следующей прошивке нужна другая работа с драйвером/ядром, она получает
свою реализацию. Повторное использование существующего backend допускается
после проверки его предположений на новой сборке, а не только смены номера в JSON.

## Бинарные ресурсы

Модули хранятся в `assets/firmware/<profile-id>/`, общие версионированные файлы —
в `assets/common/`. Несколько профилей могут явно ссылаться на один проверенный
ресурс. Сборка приложения сама не пересобирает ядро или KernelSU.

Перед исполнением режимов KernelSU файлы извлекаются в device-protected
`files/firmware/<profile-id>/`, хешируются и заменяются через временный файл.
Несовпадение любого хеша останавливает этот запуск до native root. Старые плоские
`files/ksu.ko` и `files/ksud` больше не используются. Ресурсы каждого профиля
обновляются из установленного APK при каждом запуске загрузки.

Текущая `.ko` содержит собственные привязки ABI, включая SELinux/VFS. Для
другой прошивки может потребоваться отдельная сборка KernelSU даже при повторном
использовании общего интерфейса приложения.

## Добавление поддержки обновления

Ядро можно извлечь из boot image в OTA с проверкой хеша `@AML`, затем
восстановить символы и автоматически найти `sys_call_table`. Для расшифровки
пока нужен аппаратный crypto driver станции; установка исследуемой прошивки
не обязательна. Команды и проверенные результаты для трёх профилей:
[tools/ota/README.md](../../tools/ota/README.md).

1. Зафиксировать идентичность реальной сборки. Для существующего Android 11
   используются `Build.DEVICE`, `Build.MODEL`, `Build.FINGERPRINT`,
   `Build.VERSION.INCREMENTAL`, `Build.VERSION.SDK_INT`, `Os.uname()` и
   `Os.sysconf(_SC_PAGESIZE)`. Эти значения доступны без root и попадают в отчёт.
2. Проверить ABI и способ загрузки для этой сборки. Если нужна новая реализация,
   добавить `backends/<имя>/`, запись `CHIRORU_BACKEND(...)` в реестр и исходники
   в `CMakeLists.txt`. Существующая реализация остаётся отдельной.
3. Добавить точный `match` и `root.backend` в новую запись `profiles.json`.
   Для root-only этого достаточно; `.ko` и CLI не требуются. Для поддержки
   KernelSU подготовить соответствующие бинарные ресурсы и добавить блок
   `kernelSu` с backend ID, путями и фактическими SHA-256.
4. Добавить сценарий выбора новой сборки и близких несовпадающих сборок в тесты.
   Проверить маршрутизацию к нужному backend и ресурсу через подставное исполнение.
5. Собрать и проверить:

   ```sh
   ./build-apk.sh :app:testDebugUnitTest :app:lintRelease :app:testFirmwareCatalog :app:testNativeProcessWait
   ```

   `preBuild` сверяет все профили, backend ID и хеши объявленных ресурсов KernelSU;
   root-only профиль собирается без этих файлов. `testFirmwareCatalog` проверяет
   обе формы каталога и ошибки частичной декларации. Тесты Android/JVM
   используют подставное исполнение: они не запускают root на компьютере.
6. Выполнить отдельную проверку на целевой прошивке и сохранить результаты.
   Проверка APK/JVM не заменяет подтверждение поведения ядра на устройстве.

На момент переноса архитектуры в каталоге только `chiron-5000001307`.
Другие обновления автоматически поддерживаемыми не становятся.

## Проверка переноса

Сборка 0.4.0 (`versionCode=19`): 49 JVM/UI-тестов, lint Release, существующие
проверки PTE cleanup и process wait прошли. Хеши обоих ресурсов проверены также
в готовом APK. После установки обновлением на станцию главная страница показала
`Профиль: Duo Max · 5000001307`; установлен один пакет Chiroru, SELinux — Enforcing.
При этой проверке открывался только интерфейс: новый путь root/module после
рефакторинга на устройстве повторно не запускался. Проверка самой `.ko` описана
в `duomax-ksu/reports/ksu-selinux-transaction-device-2026-11-01.md`.

Разделение в 0.4.1 (`versionCode=20`): прошли 58 JVM/UI-тестов, 6 тестов
валидатора каталога, PTE cleanup и lint Release. SHA-256 ресурсов проверены
в готовом APK; `libchiroru.so` побайтно совпадает с библиотекой 0.4.0.
На станции после установки отображаются профиль `5000001307` и независимые
статусы `Root: доступен · KernelSU: доступен`. Установлен один Chiroru,
обновлятор остаётся отключённым, SELinux — Enforcing. Root-only без ресурсов
проверен на подставном backend; нативные root/module операции в этой проверке
на устройстве не запускались.
